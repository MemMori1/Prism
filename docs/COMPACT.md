# `/compact`：把长会话压成一份交接摘要

> 一句话：**重写会话文件，而不是打个标记**。上下文是真正发给模型的那份数据，
> 标记不会让它变小；只有把原文换掉，下一次请求才真的省 token。

代码：`src-tauri/src/engines/native/compact.rs`（逻辑）、`store::replace_messages`（落盘）、
`src/components/SessionView.vue` / `TimelineItem.vue`（进度与摘要卡）。

---

## 1. 为什么不直接用「更大的上下文」

模型窗口再大也是有限的，而且**每一轮都要重发整份历史**：十万 token 的会话，
每问一句就付十万 token。压缩不是省窗口，是省每一轮的账单，顺带让模型别在
几十条工具输出里迷路。

## 2. 命令形态

```
/compact
/compact 只留 API 契约和待办，实现细节可以丢
```

- 命令名出现在原生引擎的 `catalog.commands` 里，所以在输入框敲 `/` 就能选到
  （`Engine::catalog` → 前端 `/` 弹层直接读它，没有第二份清单）。
- 后面跟的文字是「本次压缩的额外要求」，原样塞进摘要提示词的最后一段。
- 会话里少于 2000 字符时不做（摘要本身也要一千多字，压完更难读），
  返回一句「压缩没有意义（原样保留）」。

## 3. 怎么压

1. **渲染**：每条消息变成一行事实——`【用户】…` / `【助手】…` / `【调用 工具名】入参`
   / `【工具结果】…`。工具结果裁到 1500 字符，入参裁到 400 字符：
   摘要要的是结论，不是整段 `cargo build` 输出。
2. **切段**：按 4 万字符装箱（≈1.5 万 token）。一段一次模型调用。
3. **滚动合并**：第一段从零写；后面每段都是「已有摘要 + 新增对话 → 新摘要」，
   规则里写死「已有结论不要丢，被后文推翻的要改掉」——否则多段压缩会前后矛盾。
4. **上限**：最多 8 段。超了只留**最近** 8 段（越近越重要），并在摘要开头如实写
   「更早的 N 条消息超出压缩上限，未纳入摘要」。宁可少一点历史，也不能悄悄丢掉
   还宣称压缩完了。
5. **落盘**：会话里只剩一条 `role = "compact"` 的消息（摘要正文），外加**如果最后
   一条是没人回答的用户消息，把它留着**——那是当下的问题，不该被压没。

摘要提示词要求固定四节：`## 目标` / `## 已完成` / `## 关键文件与命令` / `## 待办与约束`。
「待办」是接手的人最需要的一段，所以单独列，并且要求写清卡在哪。

## 4. 发给模型时的样子

摘要以 **user 消息** 送出，前面加一句身份说明：

```
（以下是此前对话的压缩摘要，作为已知背景。不要回应这段摘要本身，等我下一条指令。）
```

- 不用第二条 `system`：多数 OpenAI 兼容端只认开头那一条，中途插 system 有的直接 400。
- 那句说明不能省。省掉之后模型经常把摘要当新指令，回一句「好的，我继续」然后停住。
- 摘要与真正的用户消息之间是硬边界（清空孤儿工具结果配对），
  和普通 user 消息一致——见 `provider_messages` 里 `"compact"` 分支。

## 5. 界面：就发生在会话里

压缩是会话历史的一次改写，所以它的痕迹也应该在**会话时间轴**上，而不是一个
飘在输入框上方的进度条（那个位置说的是「我要发消息」，不是「历史被改了」）。

时间轴上是三行（`role = system` 的分隔线）：

```
───────── 会话压缩已开始 · 12 条消息 · 41203 字符 ─────────
┌ 上下文已压缩 · 此前的对话已并入下面的摘要       展开 ┐
│  ## 目标 / 已完成 / 关键文件与命令 / 待办与约束        │
└──────────────────────────────────────────────────┘
───────── 会话压缩已结束 · 12 条消息 · 41203 → 1830 字符 ─────────
```

- **开始**：`/compact` 一发起就把这一行**落库**（`session.compact.started` 让前端
  读一次尾页）。中途崩了也留得下——那本来就是发生过的事。
- **进行中**：还没吐字的那一轮 live 块，提示从「等待模型响应…」换成
  「正在压缩上下文 · 第 2/3 段」（`session.compact.progress`）。**跑在会话里**，
  而不是另起一个进度条。
- **结束**：`store::replace_messages` 把整份历史换成「开始行 + 摘要 + 结束行」
  （外加没人回答的那条用户消息）。结束行上写明压了多少：这是用户唯一能核对
  「有没有白跑」的地方。
- **取消**：历史原样保留，只补一行「会话压缩已取消 · 历史原样保留」，
  别让开始那一行悬在那儿没有下文。
- **失败**：同样补一行「会话压缩失败：<原因>」，错误同时弹一次提示。
- 这三类标记都是 `role = system`：**不发给模型**，所以它们不花一分 token。

- **运行态**：压缩和跑回合共用同一个「会话忙」槽位（`agent::RunSlot`），
  所以停止按钮能打断它，执行中新发的消息会按既有规则排队、结束后自动发出；
  反过来说，**一轮还在跑的时候不能压缩**——输入 `/compact` 只会得到一句
  「得等这一轮结束」，不会排进队列（队列只存文字，命令排进去会被当成普通消息
  发给模型）。

## 6. 安全与回退

- **先备份**：`messages.jsonl.bak`（只留最近一次）。摘要写歪了，把这个文件换回
  `messages.jsonl` 再重压一次即可。
- **原子替换**：写 `messages.jsonl.tmp` 再 rename，半路断电不会留下半份会话。
- **用量入账**：摘要调用的 input/output 记进会话累计——它也是真金白银。
- 压缩不碰项目文件，也不执行任何工具：只读会话、写会话。

## 7. 已知边界

- 有损。摘要没写下来的细节就没了，所以提示词要求「文件用完整路径、命令写原样、
  测试写数字」。
- 只做原生引擎。另外四家的历史在各自应用里，我们没有改写入口（Codex / dsh 连
  斜杠命令都不接）。
- 不做**主动**压缩。什么时候该压是用户的判断：压完模型会「忘掉」细节，
  这个决定不该由程序替人做。
- 压缩期间不能再发消息（同一会话只能有一个在跑的东西）：排队或等它结束。

## 8. 超限救援（唯一的自动压缩）

唯一的例外：**模型把请求整个拒了**——上下文超限的 400
（`maximum context length` / `context_length_exceeded` / `prompt is too long`）。
这不算「程序替用户判断时机」：请求已经发不出去了，会话卡死，每按一次发送
烧一次全额 token 还原样失败。这时回合循环自动跑一次压缩（§3 全套机器），
压完重载历史重发，会话自己救活。

- **不烧轮次**：救援重试不计入 turn 上限——它消耗的是被拒的那次请求。
- **上限 3 次**：压完历史只剩摘要（几千 token），正常一次就够；跑满三次
  说明有什么在造巨量输出，如实把原始错误交还给用户。
- **时间线上看得见**：开始标记写明「上下文超限，自动压缩开始」，
  `session.compact.*` 事件带 `auto: true`，和手动 /compact 用同一套卡片。
- **压缩本身也可能失败**（比如摘要模型也不可用）：那就把两个错误一起
  交还用户，历史已由 `messages.jsonl.bak` 兜底。
- 认关键词不解析 JSON：错误 detail 只留 400 字符，各家 400 的形状不同，
  但关键词都在开头（`provider::is_context_overflow`）。

### 8.1 编排节点：同一台机器，不落盘

编排的节点跑的是同一个原生引擎，但**没有会话文件**——它的历史是一个内存里的
`Vec<Value>`，跑完就没了。所以它只借摘要那一步（`compact::summarize_lines`：
分块、滚动合并、8 段上限、4 万字符装箱全都一样），重组由
`overflow::compress_messages` 负责。

| | 聊天 | 编排节点 |
|---|---|---|
| 入口 | `/compact` 或自动救援 | 只有自动救援（无人值守，没人能敲命令） |
| 结果去向 | 写回 `messages.jsonl`（开始/摘要/结束三行） | 替换内存里的消息数组，跑完即弃 |
| 保留结构 | 摘要 + 没人回答的那条用户消息 | `system` + 任务原文 + 摘要 + **最后一个完整回合** |
| 救援上限 | 3 次（全是压缩） | 2 次：**第一次压缩，之后退回机械裁剪** |

几个刻意的选择：

- **先压缩、后裁剪**。裁剪（`trim_messages`）是纯丢：删掉的工具结果再也回不来。
  一个节点读几十个文件、跑几遍测试是十几分钟的事，而一次摘要调用只要几千 token。
  能压就压，压不动（没有中段、摘要模型也失败）才退回裁剪。
- **末尾一整轮不动**。assistant 的 `tool_calls` 和它的 tool 结果是不可分的一对，
  从中间切会留下没人认领的调用，下一轮请求当场 400。切点由
  `overflow::compaction_cut` 取「最后一个 assistant」，单测锁住了这条。
- **`system` 不进摘要**。它是这一轮的规则，压掉等于把规矩丢了。
- **救援失败也要说清楚**。错误里带「已自动压缩与裁剪仍装不下」和最后五步工具调用
  ——否则用户只看到一句 `maximum context length`，以为节点整个白跑了。

### 8.2 工具出口闸：不依赖每个工具自觉

超限的第一道防线不在救援，在**源头**：`tools::run_with_args` 是所有工具调用的
唯一出口（聊天、编排、子代理三条路都从这里过），它在返回前统一把文本截到
`MAX_OUTPUT_CHARS`（4 万字符，头 3/4 + 尾 1/4）。

为什么必须收口在这一层：各工具自己 `clamp` 是「自觉」，而 `bin.*` 那批的输出
量**取决于样本**——反汇编、strings、jq 查询一个 8 MB 的 JSON，出来多少字符
事先不知道。实测踩过一次：一个节点连调 8 次 `artifact.get` 加两次
`bin.json.jq`，单次请求到了 **1,912,711 token**，1M 窗口的模型直接 400，节点
当场废掉。工具各自限流时，只要有一个漏了就是这种结果。

几条约束：

- **4 万这个值对齐 `artifact_tools::GET_LIMIT`**。制品读取本来就要给到这个量，
  出口再压会让「读得出来」变成假话。
- **头尾都留，不只留头**。编译错误、panic、JSON 的收尾都在尾部；只留头会让
  「到底哪一步失败」整段消失，模型只能猜。
- **`bin.json.jq` 另有字符预算**（`JSON_OUTPUT_CHARS` 3 万）。它原来按「值的
  个数」限流（5000 个），但一个值本身可能就是十万字符的字符串——按个数根本
  管不住总量。
